## 0. Основа

### База данных — это таблицы

Самая близкая аналогия — книга Excel:

| Excel | База данных |
|---|---|
| файл `.xlsx` | **база данных** (`library`) |
| лист | **таблица** (`book`, `author`) |
| строка | **запись** — одна книга, один автор |
| столбец | **поле** (колонка) — `title`, `year` |
| ячейка | значение поля у конкретной записи |

Пример таблицы `book`:

| id | title | year | author_id |
|---|---|---|---|
| 1 | Властелин колец | 1954 | 1 |
| 2 | Ведьмак | 1993 | 2 |
| 3 | Хоббит | 1937 | 1 |

Главное отличие от Excel: у каждого столбца **строгий тип**. В `year` нельзя записать «давно», только число.

### СУБД, MySQL и SQL

- **СУБД** (система управления базами данных) — программа, которая хранит базы, следит за порядком и выполняет запросы. **MySQL** — одна из самых популярных СУБД.
- MySQL — **отдельная программа-сервер**. В MAMP она запускается вместе с Apache (порт **8889**).
- **SQL** — язык, на котором с СУБД разговаривают: «создай таблицу», «дай все книги 1950-х», «удали пользователя № 5».

Кто с кем общается:

```
браузер  ──HTTP──►  Apache + PHP  ──SQL──►  MySQL
         ◄──HTML──                ◄──строки──
```

PHP для MySQL — **клиент**: он отправляет SQL-запрос, получает ответ (строки таблицы) и превращает их в HTML. Браузер про базу ничего не знает.

### Типы данных столбцов

| Тип | Что хранит | Пример |
|---|---|---|
| `INT` | целое число | `id`, `year`, количество страниц |
| `SMALLINT` | небольшое целое (до 32 767) | год |
| `DECIMAL(10,2)` | точное дробное — для денег | `199.99` |
| `VARCHAR(n)` | строка длиной до `n` символов | `VARCHAR(200)` — название |
| `TEXT` | длинный текст | описание, отзыв |
| `DATE` | дата `ГГГГ-ММ-ДД` | `1954-07-29` |
| `DATETIME` | дата и время | `2026-11-16 20:26:45` |
| `BOOLEAN` | да/нет (на деле `TINYINT`: 0 или 1) | `is_available` |

Ещё два свойства столбца:

- `NOT NULL` — значение обязательно, пустым (`NULL`) быть не может;
- `DEFAULT ...` — значение по умолчанию, если его не передали. Например, `DEFAULT CURRENT_TIMESTAMP` — текущие дата и время.

### Первичный ключ и `AUTO_INCREMENT`

**Первичный ключ** (`PRIMARY KEY`) — столбец, по которому запись можно найти **однозначно**. Два одинаковых значения в нём невозможны. Обычно это `id`.

Почему не название: книг с одинаковым названием может быть несколько, а `id` уникален всегда.

`AUTO_INCREMENT` — MySQL сам выдаёт номер: 1, 2, 3… Вставляешь книгу без `id` — она получает следующий свободный номер. Это то же, что автоинкремент, который в ЛР13 надо будет сделать вручную через статическое свойство.

Условие задания 1 «в каждой таблице должен быть уникальный идентификатор» — это как раз `id INT AUTO_INCREMENT PRIMARY KEY`.

### Связи между таблицами

Почему не хранить автора прямо в книге, строкой `"Толкин"`?

- автор повторится у каждой его книги — лишнее место;
- опечатка в одной записи (`"Толкиен"`) — и это уже «другой» автор;
- переименовать автора придётся во всех книгах сразу.

Поэтому автор хранится **один раз** в своей таблице, а книга ссылается на него **номером**:

```
author                    book
┌────┬──────────────────┐ ┌────┬─────────────────┬───────────┐
│ id │ name             │ │ id │ title           │ author_id │
├────┼──────────────────┤ ├────┼─────────────────┼───────────┤
│ 1  │ Дж. Р. Р. Толкин │◄┼─┐  │ Властелин колец │ 1         │
│ 2  │ А. Сапковский    │ │ │  │ Ведьмак         │ 2         │
└────┴──────────────────┘ │ └──┤ Хоббит          │ 1         │
                          └────┴─────────────────┴───────────┘
```

`book.author_id` — **внешний ключ** (`FOREIGN KEY`): столбец, который хранит `id` записи из **другой** таблицы.

Виды связей:

| Связь            | Пример                                       | Как сделать                                                |
| ---------------- | -------------------------------------------- | ---------------------------------------------------------- |
| один-ко-многим   | у автора много книг, у книги один автор      | в «многих» (`book`) столбец `author_id`                    |
| многие-ко-многим | у книги несколько жанров, в жанре много книг | **промежуточная** таблица `book_genre (book_id, genre_id)` |
| один-к-одному    | у пользователя один профиль                  | `user_id` в профиле + `UNIQUE`                             |

Самая частая — один-ко-многим. Для лабы её достаточно: у книги один автор и один жанр.

### Внешний ключ охраняет порядок

Если внешний ключ объявлен, MySQL **сам** следит, чтобы ссылки не вели в пустоту:

- вставить книгу с `author_id = 99`, когда автора № 99 нет, — ошибка **1452** `Cannot add or update a child row: a foreign key constraint fails`;
- удалить автора, у которого есть книги, — ошибка **1451**.

Это называется **ссылочная целостность**. Без внешнего ключа `author_id` был бы просто числом, и в базе могли бы появиться книги «ничьих» авторов.

Внешние ключи работают только с движком таблиц **InnoDB**. В MySQL 8 он используется по умолчанию.

### Кодировка `utf8mb4`

Чтобы русские буквы (и эмодзи) хранились правильно, у базы и подключения должна быть кодировка **`utf8mb4`**. Сравнение строк задаёт **collation**, например `utf8mb4_unicode_ci`. Окончание `ci` — case-insensitive: при поиске «ВЕДЬ» и «ведь» совпадают. Это пригодится в задании 3.

**phpMyAdmin** — сайт для управления MySQL мышкой: создавать базы и таблицы, смотреть и править данные, выполнять SQL-запросы.

## SQL — шесть команд, которых хватит на всю лабу

Все примеры проверены в MySQL 8 из MAMP. Ключевые слова SQL принято писать заглавными — так их легче отличить от имён таблиц, но MySQL понимает и строчные.

### `CREATE TABLE` — создать таблицу

```sql
CREATE TABLE author (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

CREATE TABLE book (
    id INT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    year SMALLINT,
    author_id INT NOT NULL,
    FOREIGN KEY (author_id) REFERENCES author(id)
);
```

- внутри скобок — столбцы через запятую: **имя тип свойства**;
- `FOREIGN KEY (author_id) REFERENCES author(id)` — «`author_id` ссылается на `id` таблицы `author`».

Порядок важен: сначала создаётся таблица, **на которую** ссылаются (`author`), потом та, **которая** ссылается (`book`).

То же самое можно сделать мышкой в phpMyAdmin — он сам сгенерирует такой SQL.

### `INSERT` — добавить запись

```sql
INSERT INTO author (name) VALUES ('Дж. Р. Р. Толкин');
INSERT INTO book (title, year, author_id) VALUES ('Хоббит', 1937, 1);
```

- в первых скобках — **какие** столбцы заполняем;
- в `VALUES` — **значения** в том же порядке;
- `id` не указываем — его выдаст `AUTO_INCREMENT`;
- строки в SQL — в **одинарных** кавычках.

Несколько записей сразу: `VALUES ('А'), ('Б'), ('В')`.

### `SELECT` — прочитать записи

```sql
SELECT * FROM book;                                -- все столбцы, все записи
SELECT title, year FROM book;                      -- только два столбца
SELECT * FROM book WHERE year < 1960;              -- с условием
SELECT * FROM book ORDER BY year DESC;             -- по убыванию года
SELECT * FROM book ORDER BY title LIMIT 2;         -- первые две
SELECT COUNT(*) FROM book WHERE author_id = 1;     -- сколько книг у автора № 1
```

| Часть | Что делает |
|---|---|
| `*` | все столбцы |
| `WHERE условие` | только записи, где условие истинно: `=`, `!=`, `<`, `>`, `AND`, `OR` |
| `ORDER BY поле` | сортировка; `ASC` — по возрастанию (по умолчанию), `DESC` — по убыванию |
| `LIMIT n` | не больше `n` записей |
| `COUNT(*)` | не записи, а их количество |

`--` в SQL — комментарий до конца строки.

### `LIKE` — поиск по части строки

```sql
SELECT * FROM book WHERE title LIKE '%кол%';
```

Внутри шаблона `LIKE` два спецсимвола:

| Символ | Значит                                      | Пример     | Найдёт                                      |
| ------ | ------------------------------------------- | ---------- | ------------------------------------------- |
| `%`    | любое количество любых символов (даже ноль) | `'%кол%'`  | «Власте**лин кол**ец», «**Кол**есо времени» |
| `_`    | ровно один любой символ                     | `'Хо_бит'` | «Хоббит»                                    |

`'кол%'` — начинается на «кол», `'%кол'` — заканчивается на «кол», `'%кол%'` — содержит «кол» где угодно.

С collation `..._ci` регистр не важен: `'%ВЕДЬ%'` найдёт «Ведьмак» (проверено).

### `JOIN` — собрать данные из нескольких таблиц

В `book` вместо имени автора лежит число `author_id`. Чтобы показать имя, таблицы **соединяют**:

```sql
SELECT book.title, author.name AS author
FROM book
JOIN author ON book.author_id = author.id;
```

Результат:

| title | author |
|---|---|
| Властелин колец | Дж. Р. Р. Толкин |
| Ведьмак | А. Сапковский |
| Хоббит | Дж. Р. Р. Толкин |

- `JOIN author ON book.author_id = author.id` — «к каждой книге приклей ту строку автора, у которой `id` равен `author_id` книги»;
- `book.title` — «столбец `title` из таблицы `book`». Имя таблицы перед точкой нужно, когда столбцы с одинаковым именем есть в обеих таблицах;
- `AS author` — переименовать столбец в результате. В PHP это будет ключ `$row["author"]`.

`JOIN` можно повторять: `... JOIN genre ON book.genre_id = genre.id`.

### `UPDATE` — изменить записи

```sql
UPDATE book SET year = 1955 WHERE id = 1;
UPDATE user SET login = 'vlad', email = 'v@example.com' WHERE id = 3;
```

**Без `WHERE` изменятся ВСЕ записи таблицы.** `UPDATE book SET year = 1955` сделает все книги 1955 года. Это самая частая катастрофическая ошибка в SQL.

### `DELETE` — удалить записи

```sql
DELETE FROM book WHERE id = 3;
```

То же правило: **без `WHERE` удалится вся таблица**.

## PDO — как PHP разговаривает с MySQL

### Почему PDO, а не MySQLi

Условие разрешает оба. Оба умеют всё нужное в лабе, включая подготовленные запросы.

|                               | PDO                                                     | MySQLi              |
| ----------------------------- | ------------------------------------------------------- | ------------------- |
| с какими СУБД работает        | MySQL, PostgreSQL, SQLite и др. — код почти не меняется | только MySQL        |
| именованные параметры `:name` | есть                                                    | нет, только `?`     |
| стиль                         | только объекты                                          | объекты или функции |

PDO удобнее и универсальнее, поэтому дальше — только он. Объект, `->`, `new` — это ООП, его подробно разбирает ЛР13. Здесь достаточно: `$pdo` — «подключение», у него есть методы-команды, которые вызываются через `->`.

### `new PDO($dsn, $пользователь, $пароль, $настройки)` — подключиться

```php
$pdo = new PDO(
    "mysql:host=localhost;port=8889;dbname=library;charset=utf8mb4",
    "root",
    "root",
    [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    ]
);
```

Создаёт подключение к базе и возвращает объект-подключение. Через него дальше выполняются все запросы.

**Первый аргумент — DSN** («имя источника данных»), строка «куда подключаться»:

| Часть | Значит |
|---|---|
| `mysql:` | какая СУБД |
| `host=localhost` | на каком компьютере сервер MySQL — на этом же |
| `port=8889` | порт MySQL в MAMP (у обычного MySQL — 3306) |
| `dbname=library` | какая база |
| `charset=utf8mb4` | кодировка обмена — чтобы кириллица не превратилась в `????` |

Второй и третий — **логин и пароль** MySQL (в MAMP `root` / `root`).

Четвёртый — **массив настроек**:

| Настройка | Что делает |
|---|---|
| `PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION` | при ошибке SQL — **выбрасывать исключение**, а не молча возвращать `false`. Без этого ошибку в запросе легко не заметить |
| `PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC` | строки возвращать **ассоциативными массивами**: `["title" => "Хоббит", ...]` |

`PDO::ATTR_ERRMODE` — это **константа класса** `PDO` (запись `Класс::КОНСТАНТА`, ЛР13).

### Ошибки подключения — `try / catch (PDOException $e)`

Если подключиться не удалось, `new PDO` выбрасывает исключение `PDOException`. Без `try/catch` скрипт упадёт с длинным Fatal error, где виден пароль. Поэтому подключение оборачивают (`try/catch` — ЛР4, ЛР8):

```php
try {
    $pdo = new PDO($dsn, DB_USER, DB_PASS, $options);
    echo "Подключение к базе установлено";
} catch (PDOException $e) {
    echo "Ошибка подключения: " . $e->getMessage();
    exit;
}
```

- `$e->getMessage()` — текст ошибки;
- `exit` — без базы дальше работать бессмысленно (ЛР9).

Какие сообщения бывают (проверено):

| Сообщение | Что не так |
|---|---|
| `[1045] Access denied for user 'root'@'localhost'` | неверный логин или пароль |
| `[1049] Unknown database 'nosuchdb'` | базы с таким именем нет — опечатка в `dbname` |
| `[2002] Connection refused` / `No such file or directory` | MySQL не запущен или не тот порт — проверь, что в MAMP горит MySQL |

На настоящем сайте текст ошибки пользователю не показывают — пишут «Сервис временно недоступен», а детали — в лог. В лабе задание прямо просит «вывод сообщения о подключении», поэтому выводим.

### Настройки подключения — константами в отдельном файле

Задание: «Создайте отдельный файл для подключения к базе данных, в нём определите **константы** с именем хоста, названием базы данных, именем пользователя и паролем».

Константы (ЛР7, ЛР8) — значения, которые нельзя случайно изменить:

```php
const DB_HOST = "localhost";
const DB_PORT = 8889;
const DB_NAME = "library";
const DB_USER = "root";
const DB_PASS = "root";
```

Второй способ — `define("DB_HOST", "localhost");`. Разница: `const` — на верхнем уровне файла, `define` — можно и внутри `if` или функции.

Файл подключения (например, `db.php`) создаёт `$pdo`, а все страницы подключают его первой строкой:

```php
require_once "db.php";   // теперь здесь есть $pdo
```

`require_once` (ЛР7): без файла подключения страница работать не может, поэтому `require`, а `_once` — чтобы не подключиться к базе дважды.

Зачем отдельный файл: настройки базы записаны **в одном месте**. Сменился пароль — правишь одну строку, а не каждую страницу.

### `query($sql)` — выполнить запрос без параметров

```php
$result = $pdo->query("SELECT * FROM author");
```

Выполняет SQL и возвращает объект-результат (`PDOStatement`). Строки из него достают методами `fetch...`.

Использовать **только** для запросов, в которые не попадают данные от пользователя. Почему — в разделе «SQL-инъекция».

### `fetchAll()` — все строки массивом

```php
$authors = $pdo->query("SELECT * FROM author")->fetchAll();
```

```
[
    ["id" => 1, "name" => "Дж. Р. Р. Толкин"],
    ["id" => 2, "name" => "А. Сапковский"],
]
```

Массив строк, каждая строка — ассоциативный массив «столбец → значение» (благодаря `FETCH_ASSOC`). Дальше — обычный `foreach` (ЛР7):

```php
foreach ($authors as $author) {
    echo $author["name"];
}
```

`fetchAll(PDO::FETCH_COLUMN)` — вместо массивов строк вернуть **один столбец** простым списком: `["Дж. Р. Р. Толкин", "А. Сапковский"]`.

### `fetch()` — одна строка

```php
$author = $stmt->fetch();   // ["id" => 2, "name" => "А. Сапковский"] или false
```

Возвращает **следующую** строку результата или **`false`**, если строк больше нет (или не было вовсе). Удобно, когда ищем одну запись по `id`:

```php
if ($author === false) {
    echo "Автор не найден";
}
```

### `fetchColumn()` — одно значение

```php
$count = $pdo->query("SELECT COUNT(*) FROM book")->fetchColumn();   // 3
```

Значение первого столбца следующей строки. Идеально для `COUNT(*)`: результат — одно число.

### `exec($sql)` — выполнить запрос, который ничего не возвращает

```php
$pdo->exec("DELETE FROM book WHERE id = 3");
```

Для `CREATE`, `INSERT`, `UPDATE`, `DELETE` без пользовательских данных. Возвращает количество затронутых строк. В лабе почти не нужен — таблицы создаются в phpMyAdmin, а данные от пользователя идут через `prepare`.

### SQL-инъекция — почему нельзя вклеивать данные в запрос

Представь поиск книги по названию, где ввод пользователя просто вклеен в строку:

```php
$title = $_GET["title"];
$pdo->query("SELECT * FROM book WHERE title = '$title'");   // ОПАСНО
```

Пользователь вводит в поле: `' OR '1'='1`. Запрос получается такой:

```sql
SELECT * FROM book WHERE title = '' OR '1'='1'
```

Кавычка из ввода **закрыла** строку SQL, а дальше пошёл SQL, который написал пользователь. `'1'='1'` всегда истинно — запрос вернул **все** книги (проверено). Вместо этого можно было ввести `'; DROP TABLE user; --` или достать чужие пароли. Это **SQL-инъекция** — одна из самых опасных уязвимостей сайтов.

Как с XSS в ЛР9: данные пользователя попали в место, где их **выполнили как код**. Только там код выполнял браузер, а здесь — база данных.

Защита — **подготовленные запросы**.

### `prepare($sql)` + `execute($значения)` — подготовленный запрос

```php
$stmt = $pdo->prepare("SELECT * FROM book WHERE title = ?");
$stmt->execute([$title]);
$books = $stmt->fetchAll();
```

Запрос выполняется **в два этапа**:

1. `prepare` — отправить в MySQL **шаблон** запроса. Вместо данных — **заглушки** `?`. MySQL разбирает структуру запроса **заранее**, ещё не видя данных.
2. `execute` — отправить **данные** отдельно. MySQL подставляет их на место `?` строго **как значения**. Что бы там ни было — кавычки, `OR`, `DROP` — это просто текст, который сравнивается с названием.

Тот же ввод `' OR '1'='1` через `prepare` вернул **пустой** результат: книги с таким странным названием нет (проверено).

**Правило:** если в запрос попадает хоть что-то от пользователя (`$_GET`, `$_POST`, куки) — только `prepare` + `execute`. Задание 3 требует этого явно.

Заглушки бывают двух видов:

```php
// позиционные — значения по порядку
$stmt = $pdo->prepare("INSERT INTO book (title, year, author_id) VALUES (?, ?, ?)");
$stmt->execute(["Хоббит", 1937, 1]);

// именованные — значения по именам
$stmt = $pdo->prepare("UPDATE user SET email = :email WHERE id = :id");
$stmt->execute(["email" => "v@example.com", "id" => 3]);
```

Именованные удобнее, когда параметров много: не нужно следить за порядком.

Один подготовленный запрос можно выполнять много раз с разными данными — `prepare` один раз, `execute` в цикле.

Важно: заглушка заменяет **только значение**. Имя таблицы или столбца через `?` подставить нельзя.

### `lastInsertId()` — какой `id` получила новая запись

```php
$stmt->execute(["Хоббит", 1937, 1]);
echo $pdo->lastInsertId();   // например, "4"
```

После `INSERT` возвращает `id`, который выдал `AUTO_INCREMENT`. Пригодится для сообщения «Книга добавлена под номером 4» и для регистрации — сразу узнать `id` нового пользователя.

### `rowCount()` — сколько строк затронуто

```php
$stmt = $pdo->prepare("UPDATE book SET year = ? WHERE id = ?");
$stmt->execute([1955, 1]);
echo $stmt->rowCount();   // 1
```

После `UPDATE` / `DELETE` — сколько записей изменилось.

Подвох (проверено): если записать **то же самое** значение, что уже было, `rowCount()` вернёт **0** — для MySQL ничего не изменилось. Поэтому `0` после `UPDATE` не всегда значит «запись не найдена».

### Коды ошибок MySQL

При ошибке запроса в `PDOException` есть номер ошибки MySQL — `$e->errorInfo[1]`. По нему можно показать понятное сообщение:

| Код | Когда | Понятное сообщение |
|---|---|---|
| **1062** | `Duplicate entry` — повтор в столбце с `UNIQUE` / `PRIMARY KEY` | «Такой e-mail уже зарегистрирован» |
| **1452** | внешний ключ ссылается на несуществующую запись | «Такого автора нет» |
| **1451** | удаление записи, на которую ссылаются другие | «Нельзя удалить автора, у него есть книги» |
| **1045** | неверный логин/пароль подключения | «Ошибка подключения к базе» |
| **1049** | нет такой базы | «Ошибка подключения к базе» |

```php
try {
    $stmt->execute([$title, $year, $authorId]);
    echo "Книга добавлена";
} catch (PDOException $e) {
    if ($e->errorInfo[1] === 1452) {
        echo "Ошибка: такого автора нет";
    } else {
        echo "Ошибка базы данных: " . $e->getMessage();
    }
}
```

`$e->getCode()` вернёт другое — общий код SQLSTATE `"23000"` («нарушение целостности»), одинаковый и для 1062, и для 1452. Поэтому различать удобнее по `errorInfo[1]`.

### Вывод данных из базы — через `htmlspecialchars`

Данные в базе когда-то ввёл пользователь. Значит, при выводе в HTML — `htmlspecialchars` (ЛР9, защита от XSS). Сохранить в базу `<script>` можно — главное, не выполнить его при показе.

### Часть 1. Проектирование — как придумать схему

Порядок мыслей:

1. **Сущности** — о чём хранить данные. Каждая сущность — таблица: книга, автор, жанр.

4. **Связи** — кто на кого ссылается. Задай вопрос «у одной книги сколько авторов? у одного автора сколько книг?». Ответ «один — много» → внешний ключ в таблице «много».

Тема не обязана быть про книги: фильмы — режиссёры — жанры, игры — студии — платформы, блюда — повара — кухни. Но книги совпадают с примером из задания и пригодятся в задании 3 (поиск по `Book`).

### Как нарисовать схему «по стандартам»

Стандартная схема базы данных — **ER-диаграмма** (Entity–Relationship, «сущность — связь»):

- каждая таблица — **прямоугольник**: сверху имя таблицы, ниже столбцы с типами;
- первичный ключ помечается **PK** (или значком ключа, или подчёркиванием);
- внешний ключ — **FK**;
- связь — **линия** между внешним ключом и первичным ключом, на который он ссылается;
- вид связи — на концах линии. В самой распространённой нотации «crow's foot» («воронья лапка»): одна черта `|` — «один», разветвление `<` — «много».

```
┌──────────────────────┐            ┌──────────────────────────┐
│ author               │            │ book                     │
├──────────────────────┤            ├──────────────────────────┤
│ PK id       INT      │──┼─────────<│ PK id         INT        │
│    name     VARCHAR  │            │    title      VARCHAR    │
│    country  VARCHAR  │            │    year       SMALLINT   │
└──────────────────────┘            │ FK author_id  INT        │
                                    │ FK genre_id   INT        │
┌──────────────────────┐            └──────────────────────────┘
│ genre                │                         ┃
├──────────────────────┤                         ┃
│ PK id       INT      │──┼──────────────────────┛ (много книг)
│    title    VARCHAR  │
└──────────────────────┘
```

`──┼───<` читается: «один автор — много книг».

Чем нарисовать: от руки на листе (разрешено), **draw.io** (diagrams.net, раздел *Entity Relation*), **dbdiagram.io**, или вкладка **Дизайнер** в phpMyAdmin — она рисует схему по уже созданным таблицам.

### Как сделано в лабе

**Схема** — файл `schema.svg`, показан на `lab11.php`. Четыре таблицы:

| Таблица | Столбцы | Связи |
|---|---|---|
| `author` | `id`, `name`, `country` | — |
| `genre` | `id`, `title` (`UNIQUE`) | — |
| `book` | `id`, `title`, `year`, `author_id`, `genre_id` | `author_id` → `author.id`, `genre_id` → `genre.id` |
| `user` | `id`, `login`, `email` (`UNIQUE`), `password_hash`, `salt`, `created_at` | — (задание 4) |

**Таблицы и данные** — файл `library.sql`: `CREATE DATABASE`, четыре `CREATE TABLE` с внешними ключами и `INSERT` (5 авторов, 4 жанра, 9 книг, 4 пользователя). Это тот же SQL, который phpMyAdmin генерирует, когда таблицы создаются мышкой. На защите можно показать любой способ.

**Файл подключения — `db.php`:**

```php
const DB_HOST = "localhost";
const DB_PORT = 8889;
const DB_NAME = "library";
const DB_USER = "root";
const DB_PASS = "root";

try {
    $pdo = new PDO(
        "mysql:host=" . DB_HOST . ";port=" . DB_PORT . ";dbname=" . DB_NAME . ";charset=utf8mb4",
        DB_USER,
        DB_PASS,
        [
            PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        ]
    );
    $dbMessage = "Подключение к базе «" . DB_NAME . "» установлено";
} catch (PDOException $e) {
    echo "<p style='color: red'>Ошибка подключения к базе данных: ", htmlspecialchars($e->getMessage()), "</p>";
    exit;
}
```

Три момента, которые стоит понимать:

1. **DSN склеен точками.** Константы, в отличие от переменных, **не подставляются** внутри двойных кавычек: `"host=DB_HOST"` так и останется текстом `DB_HOST`. Поэтому `"mysql:host=" . DB_HOST . ";port=" ...`.
2. **Сообщение о подключении сохраняется в переменную `$dbMessage`, а не выводится сразу.** `db.php` подключается **первой строкой**, ещё до `<html>`. Если там сделать `echo`, то `header("Location: ...")` на странице (PRG в заданиях 2, 4, 5) перестанет работать: заголовки нельзя отправить после того, как вывод уже начался (ЛР9). Каждая страница сама печатает `<?= $dbMessage ?>` в нужном месте.
3. **При ошибке — `echo` и `exit`.** Тут вывод до `<html>` не страшен: страница всё равно дальше не работает. Проверено: с неверным паролем выводится `[1045] Access denied for user 'root'@'localhost'`, с неверным именем базы — `[1049] Unknown database 'nosuchdb'`. Fatal error с паролем на экране не появляется.

VS Code подчёркивает `$dbMessage` и `$pdo` на страницах: «Undefined variable». Это ложная тревога, как с `$xss` в ЛР10 — редактор не видит, что переменные пришли из `require_once "db.php"`.

**Страница таблиц — `task1.php`:**

```php
$tables = $pdo->query("SHOW TABLES")->fetchAll(PDO::FETCH_COLUMN);
// ["author", "book", "genre", "user"]
```

Дальше для каждой таблицы: `SELECT * FROM $table` → `fetchAll()` → `<table>`. Заголовки столбцов — `array_keys($rows[0])`, значения — вложенный `foreach` по строке. Пустую таблицу проверяет `count($rows) === 0`. `NULL` из базы выводится словом `NULL` благодаря `$value ?? "NULL"`.

В HTML-части используется запись `foreach (...):` … `endforeach;` и `if (...):` … `else:` … `endif;`. Это та же конструкция, что с фигурными скобками, только удобнее, когда между PHP-кусками идёт HTML (так было и в ЛР10).

## Задание 2 — добавление данных через формы

### Путь данных

Всё это уже было в ЛР9, добавляется только последний шаг:

```
форма (POST)  →  $_POST  →  проверка  →  prepare + execute (INSERT)  →  сообщение
```

### Форма для таблицы со связями

Для `author` и `genre` формы простые — одно-два текстовых поля.

Для `book` нужен выбор автора и жанра. Пользователь не должен вводить `author_id` руками — он не знает номеров. Нужен **выпадающий список из базы**:

```php
$authors = $pdo->query("SELECT id, name FROM author ORDER BY name")->fetchAll();
```

```html
<select name="author_id">
    <option value="1">Дж. Р. Р. Толкин</option>
    <option value="2">А. Сапковский</option>
</select>
```

Пункты строятся `foreach` по `$authors`: `value` — `id` (уйдёт на сервер), текст — имя (видит человек). Это та же связка `value` / текст, что в ЛР9 (выбор языка), только пункты пришли из базы.

### Проверка данных перед вставкой

Как в ЛР9 (регистрация) — массив `$errors`:

- обязательные поля не пустые (`trim`, `=== ""`);
- числа — числа: `(int) $_POST["year"]`, разумный диапазон;
- длина не больше, чем позволяет столбец (`VARCHAR(200)` → `mb_strlen <= 200`).

Если ошибок нет — `INSERT` через `prepare` + `execute`.

### Обработка ошибок базы

После успешного `INSERT` — «Книга «Хоббит» добавлена (id = 4)» через `lastInsertId()`.

Чтобы F5 не добавил запись второй раз — **PRG** (ЛР9): после успеха `header("Location: ...?added=4")` + `exit`, а сообщение показать по параметру в адресе.

## Задание 3 — поиск по таблице `Book`

> Создайте форму поиска по таблице `Book`. Пользователь вводит часть названия, а скрипт выводит все соответствия. При этом используйте подготовленные запросы.

### Поиск части названия — `LIKE` с `%`

«Часть названия» → `LIKE '%часть%'`.

Подвох: куда поставить `%`. Неправильно — в SQL рядом с заглушкой:

```php
$pdo->prepare("SELECT * FROM book WHERE title LIKE '%?%'");   // НЕ работает
```

Заглушка внутри кавычек — уже не заглушка, а просто символ `?` в строке.

Правильно — `%` приклеиваются к **значению**, а в SQL стоит голая заглушка:

```php
$stmt = $pdo->prepare("SELECT * FROM book WHERE title LIKE ?");
$stmt->execute(["%" . $query . "%"]);
```

Для запроса «кол» в базу уйдёт значение `%кол%` — найдёт «Властелин колец» (проверено).

### Регистр

При collation `utf8mb4_unicode_ci` поиск сам не учитывает регистр: «ВЕДЬ», «ведь», «Ведь» найдут «Ведьмак». Ни `mb_strtolower`, ни `LOWER()` не нужны.

### Особые случаи

- **Пустой запрос** — `%%` найдёт всё. Реши заранее: показывать всё или просить ввести текст.
- **`%` и `_` в самом запросе** — пользователь ввёл `_` → это «любой символ». Для лабы это обычно не важно. Если важно — экранировать их обратной чертой (`str_replace`: `%` → `\%`, `_` → `\_`).
- **Ничего не найдено** — `fetchAll()` вернул пустой массив → «Ничего не найдено».

### GET, а не POST

Поиск ничего не меняет в базе — значит, форма с `method="get"` (ЛР9, задание 7). Результат можно сохранить ссылкой: `search.php?q=кол`.

2. Прочитать `$_GET["q"] ?? ""`, `trim`.
3. `prepare("... WHERE title LIKE ?")` + `execute(["%$q%"])`.
4. Вывести результаты (с `htmlspecialchars`), или «Ничего не найдено».

## Задание 4 — пользователи, соль и хеш

> Добавьте в базу данных новую таблицу (либо модернизируйте уже созданную, если она подходит по смыслу), которая бы описывала пользователя. Создайте форму регистрации, содержащую поля ввода логина, электронной почты и пароля. Проверьте, существует ли уже пользователь с такой электронной почтой и предусмотрите поведение формы в таком случае. При добавлении пароля в базу данных добавляйте к нему случайную соль (хранящуюся, как отдельное поле) и вычисляйте хэш (например, через `md5()`, `sha1()` или `password_hash()`).
>
> Обратите внимание, что `md5()` и `sha1()` не рекомендуется использовать в реальных проектах.

### Таблица пользователей

Примерный набор столбцов:

| Столбец         | Тип                                  | Зачем                             |
| --------------- | ------------------------------------ | --------------------------------- |
| `id`            | `INT AUTO_INCREMENT PRIMARY KEY`     | ключ                              |
| `login`         | `VARCHAR(50) NOT NULL`               | логин                             |
| `email`         | `VARCHAR(100) NOT NULL UNIQUE`       | почта, **уникальная**             |
| `password_hash` | `VARCHAR(255) NOT NULL`              | хеш пароля — **не** сам пароль    |
| `salt`          | `VARCHAR(64) NOT NULL`               | соль — по условию отдельным полем |
| `created_at`    | `DATETIME DEFAULT CURRENT_TIMESTAMP` | дата регистрации, заполнится сама |

`UNIQUE` — ограничение «в этом столбце не бывает двух одинаковых значений». MySQL сам откажется вставить второй такой же e-mail (ошибка 1062).

`VARCHAR(255)` для хеша — потому что у `password_hash` длина может вырасти в будущих версиях PHP.

### Хеш — не шифрование

- **Шифрование** обратимо: зашифровал ключом — расшифровал тем же ключом.
- **Хеш** — односторонний: из пароля получить хеш легко, из хеша пароль — нельзя.

Зачем это нужно: если базу украдут, у злоумышленника будут только хеши. Чтобы проверить пароль при входе, его не расшифровывают. Хешируют введённый пароль заново и **сравнивают хеши**.

### `md5($строка)` и `sha1($строка)` — простые хеш-функции

```php
md5("secret");    // строка из 32 шестнадцатеричных символов
sha1("secret");   // строка из 40 символов
```

Возвращают хеш строки. Один и тот же вход → **всегда** один и тот же хеш.

Почему их не используют для паролей (об этом предупреждает и задание):

- они **очень быстрые** — компьютер перебирает миллиарды вариантов в секунду, и короткий пароль подбирается за минуты;
- без соли одинаковые пароли дают одинаковые хеши. В интернете есть готовые таблицы «хеш → пароль» для миллионов популярных паролей.

### Соль

**Соль** — случайная строка, которая добавляется к паролю **перед** хешированием. У каждого пользователя своя:

```
пароль "qwerty" + соль "a91f..." → хеш X
пароль "qwerty" + соль "07cd..." → хеш Y   (совсем другой)
```

Что это даёт:

- одинаковые пароли у разных людей дают **разные** хеши — по базе не видно, у кого одинаковые;
- готовые таблицы «хеш → пароль» бесполезны — их пришлось бы строить заново под каждую соль.

Соль **не секрет**: её хранят рядом с хешем, в отдельном столбце. Она нужна, чтобы при входе посчитать хеш так же.

### `random_bytes($n)` + `bin2hex()` — получить соль

```php
$salt = bin2hex(random_bytes(16));   // например "afb9d5ba3906909b4640d7598a6f486a"
```

- `random_bytes(16)` — 16 **криптографически случайных** байтов. Это надёжнее, чем `rand()` (ЛР4): тот подходит для игр, но не для безопасности;
- байты — это не текст, многие не печатаются. `bin2hex` превращает каждый байт в два символа `0–9a-f`;
- итог — строка из **32** символов (16 байт × 2).

### Два способа посчитать хеш

**Способ 1 — `sha1` (или `md5`) + своя соль.** Ровно то, что описано в задании:

```php
$salt = bin2hex(random_bytes(16));
$hash = sha1($password . $salt);
// в базу: password_hash = $hash, salt = $salt
```

Проверка при входе: взять из базы соль пользователя → `sha1($введённый . $соль)` → сравнить с хешем из базы.

**Способ 2 — `password_hash` (ЛР9).** Правильный для реальных сайтов:

```php
$hash = password_hash($password . $salt, PASSWORD_DEFAULT);
```

Проверка — `password_verify($введённый . $соль, $хеш_из_базы)` (проверено, работает).

Тонкость, которую стоит знать для защиты: `password_hash` **уже сам** добавляет случайную соль и хранит её внутри хеша. Если вызвать `password_hash("qwerty", ...)` дважды, хеши будут разные. Поэтому отдельная соль с `password_hash` — лишняя предосторожность. Но задание требует отдельное поле, так что его делаем.

Итог для выбора: `sha1` + соль — проще понять и показать; `password_hash` — правильнее. Оба выполняют задание.

### Проверка «такой e-mail уже есть»

Перед вставкой — спросить у базы:

```php
$stmt = $pdo->prepare("SELECT COUNT(*) FROM user WHERE email = ?");
$stmt->execute([$email]);
if ($stmt->fetchColumn() > 0) {
    $errors[] = "Пользователь с такой почтой уже зарегистрирован";
}
```

«Поведение формы в таком случае»: показать сообщение и **оставить** введённые логин и почту в полях (`value="..."`, как в ЛР9). Пароль обратно не подставляют — это общее правило безопасности.

Страховка: даже если два человека отправят одинаковую почту в одну секунду и обе проверки пройдут, `UNIQUE` не даст вставить вторую запись — будет `PDOException` с кодом **1062**. Её тоже стоит поймать и показать то же сообщение.

### `filter_var($значение, FILTER_VALIDATE_EMAIL)` — проверить e-mail

## Задание 5 — просмотр и изменение пользователя

> Создайте форму, с помощью которой можно увидеть и изменить информацию о пользователе.

### Какого пользователя показывать

Пока нет входа в систему (он в задании 6), пользователя можно выбрать:

- выпадающим списком всех пользователей (`SELECT id, login FROM user`);
- или параметром в адресе: `profile.php?id=3` → `$_GET["id"]`.

### Шаг 1 — показать данные в форме

```php
$stmt = $pdo->prepare("SELECT login, email FROM user WHERE id = ?");
$stmt->execute([$id]);
$user = $stmt->fetch();   // массив или false
```

Если `false` — «Пользователь не найден». Иначе — форма, в которой поля **уже заполнены** текущими данными:

```php
<input type="text" name="login" value="<?= htmlspecialchars($user["login"]) ?>">
```

Так пользователь «видит» информацию и сразу может её поправить.

`id` редактируемого пользователя должен уйти вместе с формой — например, скрытым полем `<input type="hidden" name="id">` (ЛР9, задание 4).

### Шаг 2 — сохранить изменения — `UPDATE`

```php
$stmt = $pdo->prepare("UPDATE user SET login = :login, email = :email WHERE id = :id");
$stmt->execute(["login" => $login, "email" => $email, "id" => $id]);
```

Обязательно `WHERE id = ...` — иначе изменятся все пользователи.

### Подвох: проверка почты при изменении

При регистрации проверяли «нет ли уже такой почты». При изменении этого мало: у самого пользователя эта почта **уже есть**, и он не меняя её нажал «Сохранить». Проверка «почта занята» должна **исключать его самого**:

```sql
SELECT COUNT(*) FROM user WHERE email = ? AND id != ?
```

### Смена пароля — по желанию

Если хочешь дать менять пароль: новая соль + новый хеш, тем же способом, что в задании 4. Пустое поле нового пароля → пароль не трогать.

### Сообщение после сохранения

`rowCount()` вернёт `0`, если ничего не поменяли (то же самое значение — см. `rowCount` выше). Это не ошибка — можно написать «Изменений нет».

### План задания 5

1. Выбор пользователя (`select` или `?id=`).
2. `SELECT` по `id` → форма с заполненными `value`.
3. Обработка POST: проверка полей, проверка почты `AND id != ?`, `UPDATE` через `prepare`.
4. Сообщение + PRG.

### Как сделано в лабе

Файл `task5.php`. Пользователь выбирается **выпадающим списком**, который сам отправляет форму при выборе: `onchange="this.form.submit()"`, как выбор языка в ЛР9. Форма списка — `method="get"`, поэтому выбранный пользователь попадает в адрес: `task5.php?id=2`.

**Какой `id` показывать:**

```php
$id = (int) ($_GET["id"] ?? $_POST["id"] ?? $users[0]["id"]);
```

`??` идут цепочкой: взять `id` из адреса, если его нет — из формы, если и там нет — первого пользователя из списка.

**Какой пункт списка выбран:** `<?= $u["id"] === $id ? "selected" : "" ?>`. Строгое `===` работает, потому что PDO (с PHP 8.1) возвращает числа из базы как `int`, а `$id` приведён к `int`.

**Страница состоит из двух частей:**

1. таблица «Информация»: id, логин, e-mail, дата регистрации;
2. форма «Изменить»: поля уже заполнены текущими значениями. `id` уходит скрытым полем `<input type="hidden" name="id">`.

**Сохранение:** проверка полей, затем `SELECT COUNT(*) FROM user WHERE email = ? AND id != ?` («почта занята **другим**»), затем `UPDATE user SET login = ?, email = ? WHERE id = ?` и PRG на `?id=…&saved=1`.

Что проверено:

| Действие | Результат |
|---|---|
| `?id=2` | в полях `ivan` / `ivan@example.com`, в списке выбран ivan |
| почта другого пользователя | «Почта … уже занята другим пользователем» |
| своя почта и новый логин | «Изменения сохранены», в поле новый логин |
| `?id=999` | «Пользователь не найден» |

### Личный кабинет с проверкой пароля

Задание 5, но пользователь — **текущий** (`$_SESSION["user_id"]`, а не `?id=`), и перед сохранением он вводит **текущий пароль**. Изменения применяются, только если пароль верный. Так, даже если кто-то сел за чужой компьютер с открытой сессией, поменять почту или пароль он не сможет.

### Главная «в красивом виде»

Не `print_r`, а карточки или таблица со стилями. Например, книги с авторами и жанрами через `JOIN`, с сортировкой.

### `password_verify($пароль, $хеш)` — подходит ли пароль к хешу

```php
password_verify("student123" . $salt, $hashFromDb);   // true
password_verify("student123", $hashFromDb);           // false — забыли соль
```

Пара к `password_hash` (ЛР9). Хешем пароль не расшифровывается. `password_verify` хеширует введённый пароль тем же способом и сравнивает результат с хешем из базы. Возвращает `true` или `false`.

Соль нужно добавить **так же**, как при регистрации: `$password . $salt`, в том же порядке. Без соли проверка не пройдёт (проверено).

## Что могут спросить на защите

### 1. Что такое база данных и СУБД?

База данных — организованное хранилище данных в виде таблиц. СУБД — программа, которая хранит базы и выполняет запросы к ним. Мы используем СУБД MySQL.

### 2. Что такое первичный ключ? Внешний ключ?

Первичный ключ — столбец с уникальным значением для каждой записи, по нему запись находится однозначно (обычно `id`). Внешний ключ — столбец, который хранит первичный ключ записи из другой таблицы и так связывает таблицы.

### 3. Какие бывают связи между таблицами?

Один-к-одному, один-ко-многим, многие-ко-многим. Многие-ко-многим делается через промежуточную таблицу из двух внешних ключей.

### 4. Зачем внешний ключ, если можно просто хранить число?

MySQL следит за целостностью: не даст сослаться на несуществующую запись (ошибка 1452) и удалить запись, на которую ссылаются (1451).

### 5. Что такое `AUTO_INCREMENT`?

MySQL сам присваивает новой записи следующий номер. `lastInsertId()` возвращает выданный номер.

### 6. Что такое SQL-инъекция и как от неё защититься?

Когда данные пользователя вклеиваются в текст SQL-запроса, их можно составить так, что они изменят сам запрос (`' OR '1'='1`). Защита — подготовленные запросы: `prepare` с заглушками и `execute` с данными. Данные тогда передаются отдельно от запроса и никогда не выполняются как SQL.

### 7. Чем `query` отличается от `prepare`?

`query` выполняет готовую строку SQL сразу. `prepare` отправляет шаблон с заглушками, а данные передаются потом в `execute`. Если в запросе есть данные от пользователя — только `prepare`.

### 8. Почему PDO, а не MySQLi?

Разрешены оба. PDO работает с разными СУБД, умеет именованные параметры `:name`, и при `ERRMODE_EXCEPTION` все ошибки приходят исключениями — их удобно ловить `try/catch`.

### 9. Что такое соль и зачем она?

Случайная строка, которая добавляется к паролю перед хешированием. Из-за неё одинаковые пароли дают разные хеши, а готовые таблицы подбора хешей становятся бесполезными. Хранится открыто, рядом с хешем.

### 10. Почему `md5` и `sha1` не рекомендуют для паролей?

Они слишком быстрые, их можно перебирать миллиардами в секунду. Для паролей нужна специально медленная функция — `password_hash`, которая к тому же сама добавляет соль.

### 11. Чем хеш отличается от шифрования?

Шифрование обратимо ключом, хеш — нет. Пароль при входе не расшифровывают, а хешируют заново и сравнивают хеши.

### 12. Что будет, если написать `UPDATE` или `DELETE` без `WHERE`?

Изменятся или удалятся **все** записи таблицы.

### 13. Зачем отдельный файл подключения?

Настройки базы хранятся в одном месте, все страницы подключают его через `require_once`. Сменился пароль — правится одна строка.

### SQL

| `LIMIT` | не больше N | `LIMIT 10` |

| Конструкция | Что делает | Пример |
|---|---|---|
| `new PDO($dsn, $user, $pass, $opts)` | подключиться | `"mysql:host=localhost;port=8889;dbname=library;charset=utf8mb4"` |
